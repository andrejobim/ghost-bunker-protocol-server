# Ghost Bunker Protocol v0.1

This document specifies the wire contract of the Ghost Bunker Protocol v0.1. It
describes the protocol as actually implemented by the reference server in this
repository and as defined by `proto/ghost_bunker_v1.proto`.

The protocol intentionally:

- Does not define accounts, login, signup, password recovery, or any persistent
  identity mechanism.
- Does not include an IP, remote-address, User-Agent, fingerprint, or persistent
  device-id field at the application layer.
- Does not transport plaintext chat content. The server only ever sees opaque
  ciphertext, nonces, and non-secret routing metadata.
- Does not define gRPC services. Protobuf is used purely as the wire format inside
  binary WebSocket frames.

This is an **experimental** specification at version `0.1`. It is not stable, has not
been independently reviewed, and may change before any non-experimental release.

---

## 1. Transport

- The transport is **WebSocket** as defined by RFC 6455.
- Production deployments must terminate **TLS** in front of (or inside) the server
  and use the `wss://` scheme. Local development uses `ws://`.
- The reference server exposes a single endpoint path: `/ghost-bunker`.
- All payload-carrying frames are **binary** WebSocket frames (opcode `0x2`). The
  reference server does not consume text frames; its `WebSocketConfig` keeps the
  text-frame buffer small specifically because text frames are unused.
- Each binary WebSocket frame carries **exactly one** serialized `GhostEnvelope`
  Protobuf message. There is no framing layer above WebSocket; one frame is one
  envelope.

### 1.1 Allowed origins

The reference server's `WebSocketConfig` registers the handler with
`setAllowedOrigins("*")`. This is appropriate for local development and explicitly not
appropriate for production. Operators are responsible for restricting allowed origins
before deploying.

### 1.2 Frame size and container buffer

The application-level limit on a serialized envelope is `max_envelope_bytes` (default
65 536 bytes / 64 KiB). The embedded servlet container is configured with
`maxBinaryMessageBufferSize = max_envelope_bytes + 16 384`. The headroom exists so that
slightly oversized frames are accepted by the container, decoded just enough to be
rejected by the application layer, and answered with a protocol-level `ERROR` of code
`BAD_ENVELOPE` before the connection is closed. Without this headroom, Tomcat's
default 8 KiB buffer would close the connection at the transport layer with no
protocol-level error visible to the client.

---

## 2. Wire format

The wire format is **binary Protobuf 3**. The contract is defined in
`proto/ghost_bunker_v1.proto`. All semantically meaningful messages are wrapped in a
single envelope type, `GhostEnvelope`, with a `oneof` payload.

This document refers to the Protobuf file as the source of truth for field numbers and
shape. See `docs/protobuf-contract.md` for a contract-level walkthrough; the present
document focuses on protocol semantics.

---

## 3. The `GhostEnvelope`

Every message on the wire is a `GhostEnvelope`. Common fields:

| Field | Type | Required | Notes |
|---|---|---|---|
| `protocol` | `string` | yes | Must equal `"ghost-bunker"` in v0.1. |
| `version` | `string` | yes | Must equal `"0.1"` in v0.1. |
| `message_id` | `string` | yes | A unique id per envelope generated by the sender. UUID/ULID/random string. |
| `timestamp_ms` | `uint64` | yes | Sender-side milliseconds since the Unix epoch. Implementations **must not** rely on this value for trust decisions. |
| `type` | `MessageType` enum | yes | Must match the active `oneof` branch. |
| `request_id` | `string` | optional | Correlation id for request/response flows (`SEND_ENCRYPTED_MESSAGE` ↔ `MESSAGE_ACCEPTED`). |
| `room_id` | `string` | conditional | Required on room-scoped messages (`JOIN_ROOM`, `LEAVE_ROOM`, `SEND_ENCRYPTED_MESSAGE`, fan-out frames). Must be ASCII-visible. |
| `payload` | `oneof` | yes | The actual typed payload. |

Field numbers 8 to 19 of the envelope are reserved for future use.

### 3.1 Envelope validation

The reference server's `ProtocolValidator.validateBaseEnvelope` rejects an envelope
when:

- `protocol` does not equal the configured expected value (default `"ghost-bunker"`)
  → `ErrorCode.BAD_METADATA`.
- `version` does not equal the configured expected value (default `"0.1"`)
  → `ErrorCode.UNSUPPORTED_VERSION`.
- `type` is `MESSAGE_TYPE_UNSPECIFIED` → `ErrorCode.BAD_METADATA`.

`ProtocolValidator.validateTypeMatchesPayload` then rejects envelopes whose declared
`type` does not match the populated `oneof` branch → `ErrorCode.BAD_METADATA`.

### 3.2 Decoding limits

`GhostEnvelopeDecoder.decode` rejects:

- `null` payloads → treated as an `InvalidProtocolBufferException`.
- Payloads larger than `max_envelope_bytes` → also treated as
  `InvalidProtocolBufferException`.

Any `InvalidProtocolBufferException` causes the server to emit `ErrorCode.BAD_ENVELOPE`
and close the connection with `GOODBYE` of reason `PROTOCOL_ERROR` and message
`"invalid protobuf"`.

---

## 4. Message types

The `MessageType` enum is defined in the `.proto`. The reference server distinguishes
the following classes:

- **Handshake**: `HELLO` (client → server), `WELCOME` (server → client).
- **Rooms**: `JOIN_ROOM` (client → server), `ROOM_JOINED` (server → client),
  `LEAVE_ROOM`, `ROOM_LEFT`.
- **Encrypted chat**: `SEND_ENCRYPTED_MESSAGE` (client → server),
  `MESSAGE_ACCEPTED` (server → client to the sender),
  `ENCRYPTED_MESSAGE` (server → client to other room participants),
  `MESSAGE_RECEIVED_ACK` (client → server, optional).
- **Heartbeat**: `PING` (server → client), `PONG` (client → server).
- **Connection lifecycle**: `ERROR` (server → client), `DISCONNECT` (client → server),
  `GOODBYE` (server → client).

The reference server **drives heartbeats**: it sends `PING` on a fixed interval and
expects `PONG` back. Client-originated `PING` frames are accepted but ignored.

The reference server's current implementation does not actively process `LEAVE_ROOM`,
`ROOM_LEFT`, `MESSAGE_ACCEPTED` from clients, `WELCOME` from clients, or any other
server-originated type echoed back; unexpected types for the current state lead to a
`PROTOCOL_VIOLATION` error.

---

## 5. State machine

A connection moves through the following session states, defined by
`GhostSessionState`:

```
AWAITING_HELLO  ──HELLO/ok──▶  ESTABLISHED  ──JOIN_ROOM/ok──▶  IN_ROOMS
       │                            │                              │
       │                            └─JOIN_ROOM (already in some)──┘
       │
       └── handshake timeout ──▶ ERROR(HANDSHAKE_TIMEOUT) + GOODBYE(PROTOCOL_ERROR)
```

Additional terminal states: `CLOSING`, `CLOSED`. The state `CONNECTED` is declared in
the enum but the current handler transitions a new connection directly to
`AWAITING_HELLO`.

### 5.1 Per-state acceptance

- **AWAITING_HELLO**: only `HELLO` is accepted. Anything else triggers a
  `PROTOCOL_VIOLATION` error.
- **ESTABLISHED**: `JOIN_ROOM`, `PONG`, `DISCONNECT` are accepted. `SEND_ENCRYPTED_MESSAGE`
  is rejected with `PROTOCOL_VIOLATION` ("send not allowed").
- **IN_ROOMS**: `JOIN_ROOM` (additional rooms, up to `max_rooms_per_connection`),
  `SEND_ENCRYPTED_MESSAGE`, `MESSAGE_RECEIVED_ACK`, `PONG`, `DISCONNECT` are accepted.

Repeated protocol violations (`PROTOCOL_VIOLATION`, `BAD_METADATA`,
`UNSUPPORTED_VERSION`) within the violation window
(`max_violations_in_window` per `violation_window_ms`, default 3 per 60 seconds) cause
the server to send `GOODBYE` with reason `TOO_MANY_VIOLATIONS` and close.

## 6. Handshake

### 6.1 `HELLO` (client → server)

The client opens the WebSocket and immediately sends a `HELLO` envelope.

Payload fields:

- `client_name` (optional string): free-form name of the client implementation. It
  must not be used by the server as identity.
- `nickname` (optional string): user-visible display name. Validated by the server as
  ASCII-visible (printable ASCII 0x21–0x7E) and limited to `max_nickname_chars`
  (default 32). If null or blank, the server will assign a synthetic display name
  derived from the first 6 characters of the ephemeral `user_id`
  (e.g. `"anon-3f9a2b"`).
- `capabilities` (optional `ClientCapabilities`): an advisory hint about what the
  client supports (`e2ee_supported`, `supported_cipher_suites`,
  `max_ciphertext_bytes_supported`). The current reference server reads but does not
  negotiate against these.

The reference server validates nickname using the regex `^[\x21-\x7E]+$`, so values
containing whitespace, emoji, accented characters, or any non-printable-ASCII
character are rejected with `BAD_METADATA`.

### 6.2 `WELCOME` (server → client)

On accepted `HELLO`, the server responds with a `WELCOME` envelope. Payload fields:

- `session_id`: a fresh random UUID. Scoped to this TCP connection. Not durable, not
  a credential, not linkable across reconnections.
- `user_id`: a fresh random UUID. Same scope and same constraints as `session_id`.
- `display_name`: the accepted nickname (or the synthesized `anon-…` value).
- `server_time_ms`: server-side current epoch milliseconds.
- `limits`: the effective `ProtocolLimits` for this connection (see Section 11).
- `ping_interval_ms`: the heartbeat interval the server will use for this connection.

After `WELCOME` the session transitions to `ESTABLISHED`.

### 6.3 Handshake timeout

If no `HELLO` is received within `handshake_timeout_ms` (default 5 000 ms), the server:

1. Sends an `ERROR` envelope with code `HANDSHAKE_TIMEOUT` and message
   `"handshake timeout"`.
2. Sends a `GOODBYE` envelope with reason `PROTOCOL_ERROR` and message
   `"handshake timeout"`.
3. Closes the WebSocket connection (best-effort, with a brief delay to make `GOODBYE`
   delivery deterministic).

This sequence is covered by `GhostBunkerWebSocketIT.handshake_timeout_sends_error_then_closes_with_protocol_error_reason`.

## 7. Rooms

### 7.1 Joining a room

The client sends `JOIN_ROOM` with `room_id` set on the envelope. The `JoinRoom`
payload also carries a `room_id` field as a redundant copy; the server resolves the
effective room id by preferring `GhostEnvelope.room_id` and falling back to the
payload field if the envelope-level field is empty.

`ProtocolValidator.validateRoomId` rejects:

- `room_id` null or blank → `BAD_METADATA` ("room_id required").
- `room_id` length exceeding `max_room_id_chars` (default 64) → `BAD_METADATA`.
- `room_id` containing characters outside printable ASCII → `BAD_METADATA`.

If the connection is already in `max_rooms_per_connection` distinct rooms (default 5),
joining a **new** room returns `ErrorCode.TOO_MANY_ROOMS`. Re-joining a room the
connection is already in does not count against the limit.

On success the server responds with `ROOM_JOINED`. The payload contains:

- `room_id`: the joined room id.
- `online_count`: the current participant count in that room.

The session transitions to (or stays in) `IN_ROOMS`. There is no acknowledgment to
other participants when someone joins — the encrypted channel is responsible for any
in-band presence signaling.

### 7.2 Leaving a room

The `LEAVE_ROOM` and `ROOM_LEFT` message types exist in the `.proto` and pass through
the validator. The current handler does not implement explicit per-message leave: room
membership is cleaned up when the connection closes, via
`InMemoryRoomRegistry.leaveAll`. The reference server simply removes the closing
session from every room, and any room left empty is garbage-collected.

### 7.3 Lifetime and persistence

Rooms exist for the lifetime of the JVM. There is no persistent room directory, no
room ownership, no membership history. When a room becomes empty it is removed from
the registry. Restarting the server destroys all room and session state.

## 8. Sending an encrypted message

The encrypted send/route flow is the core operation of the protocol.

### 8.1 `SEND_ENCRYPTED_MESSAGE` (client → server)

The client sends an envelope with `type = SEND_ENCRYPTED_MESSAGE`, the target
`room_id` on the envelope, and a `SendEncryptedMessage` payload containing:

- `client_message_id`: a client-generated id for deduplication or correlation within
  the active session.
- `key_id`: a non-secret identifier helping clients select which local room key was
  used to encrypt this payload. The server treats it as opaque.
- `cipher_suite`: from the `CipherSuite` enum. The mandatory reference suite in v0.1
  is `PBKDF2_HMAC_SHA256_AES_256_GCM`. The server requires a non-unspecified value.
- `nonce`: the AEAD nonce / IV (12 bytes recommended for AES-GCM). The server
  treats it as opaque bytes; it only checks that it is non-empty.
- `ciphertext`: the encrypted chat payload. Must never contain plaintext. Server-side
  validation rejects empty ciphertext and ciphertext larger than
  `max_ciphertext_bytes` (default 16 384 bytes / 16 KiB).
- `aad_version`: a non-secret hint about the AAD construction version. Routed through
  but not interpreted by the server.

The server validates the room scope, that the session is actually in that room
(otherwise `ErrorCode.NOT_IN_ROOM`), and that the per-connection message rate limit
is not exceeded (otherwise `ErrorCode.RATE_LIMITED_CONNECTION` with
`retry_after_ms = 1000`).

### 8.2 `MESSAGE_ACCEPTED` (server → sender)

If the envelope is accepted, the server immediately replies to the **sender** with
`MESSAGE_ACCEPTED`, echoing:

- `request_id`: the value from `GhostEnvelope.request_id` if present.
- `client_message_id`: from the original `SendEncryptedMessage`.
- `server_message_id`: a freshly generated UUID identifying this routed message.
- `room_id`: the room the message was sent to.
- `accepted_at_ms`: the server's current epoch milliseconds.

### 8.3 `ENCRYPTED_MESSAGE` (server → other room participants)

After replying to the sender, the server fans out an `ENCRYPTED_MESSAGE` envelope to
every other participant of the same room (excluding the sender). The payload contains:

- `server_message_id`: the same id sent in `MESSAGE_ACCEPTED`.
- `from_user_id`: the sender's ephemeral `user_id` (the value generated for that
  session in `WELCOME`).
- `key_id`, `cipher_suite`, `nonce`, `ciphertext`, `aad_version`: copied verbatim
  from the inbound `SendEncryptedMessage`.
- `sent_at_ms`: the server's current epoch milliseconds.

The server does not decrypt, inspect, modify, or persist the ciphertext. It only
copies the bytes between WebSocket sessions.

### 8.4 `MESSAGE_RECEIVED_ACK` (client → server, optional)

A receiving client may emit `MESSAGE_RECEIVED_ACK` with the `server_message_id`,
`room_id`, and `received_at_ms`. The reference server accepts this message in the
`IN_ROOMS` state and discards it — there is no persistence and no fan-out of receipts.
This is intentional: any meaningful read receipts must be carried inside the
encrypted payload.

## 9. Heartbeat

The reference server drives heartbeats. After a connection is established, the
`HeartbeatService` schedules a fixed-rate task at `ping_interval_ms` (default
30 000 ms) which:

1. If the connection has been idle (no inbound activity) longer than `idle_timeout_ms`
   (default 90 000 ms), the server sends `GOODBYE` with reason `IDLE_TIMEOUT` and
   closes.
2. If a previous `PING` was sent and no `PONG` has been received within
   `pong_timeout_ms` (default 10 000 ms), the server sends `GOODBYE` with reason
   `PONG_TIMEOUT` and closes.
3. Otherwise, the server sends a `PING` envelope with a fresh random nonce and
   records the send time.

Clients are expected to reply with `PONG` echoing the nonce. The reference server
updates `lastPongAtMs` on any received `PONG`. A client may also emit its own `PING`
frames; the reference server accepts and ignores them, since it is the server that
drives liveness.

## 10. Errors

The server signals protocol errors with an `ErrorMessage` payload inside a `GhostEnvelope`
of type `ERROR`. Fields:

- `code`: an `ErrorCode` enum value.
- `message`: a **public canonical** short sanitized string derived from `code`.
  Implementations must not include payload, ciphertext, headers, IPs, or secrets in
  this field — and in particular, **client input must never be used** to construct
  `ErrorMessage.message`. In the reference server, the message is chosen from a fixed
  `ErrorCode → message` table owned by `ProtocolErrorMapper`.
- `request_id`: when applicable, the `request_id` from the inbound envelope.
- `retry_after_ms`: when applicable, a suggested backoff. Used by the rate-limited
  case (1 000 ms).

The `ErrorCode` enum values used by the reference server today are:

| Code | When it is emitted |
|---|---|
| `UNSUPPORTED_VERSION` | Inbound envelope's `version` does not match the configured expected version. |
| `BAD_ENVELOPE` | Decoding failed: invalid Protobuf bytes, oversized envelope. Followed by `GOODBYE`. |
| `BAD_METADATA` | Bad `protocol`, missing `type`, type/payload mismatch, bad nickname, bad `room_id`, missing fields in `SendEncryptedMessage`. |
| `CIPHERTEXT_TOO_LARGE` | `SendEncryptedMessage.ciphertext` exceeds `max_ciphertext_bytes`. |
| `TOO_MANY_ROOMS` | The connection already holds `max_rooms_per_connection` rooms and asked to join another. |
| `NOT_IN_ROOM` | Tried to send to a room the connection has not joined. |
| `HANDSHAKE_TIMEOUT` | No `HELLO` received within `handshake_timeout_ms`. |
| `PROTOCOL_VIOLATION` | Message arrived in a state where it is not allowed (e.g. `JOIN` before `HELLO`, `SEND` before `JOIN`). |
| `RATE_LIMITED_CONNECTION` | Per-connection command or message rate exceeded. Carries `retry_after_ms = 1000`. |

Other codes (`PAYLOAD_TOO_LARGE`, `CLIENT_TOO_SLOW`, `INTERNAL_ERROR`,
`ERROR_CODE_UNSPECIFIED`) are reserved by the wire contract but are not currently
emitted by the reference server.

After certain errors, the server proceeds to close the connection with `GOODBYE` (see
Section 12).

## 11. Limits

The server advertises its effective `ProtocolLimits` to the client inside `WELCOME`.
Defaults are taken from `GhostBunkerProperties.Limits` and exposed through
`ProtocolLimits`:

| Limit field (wire) | Default | Notes |
|---|---|---|
| `max_envelope_bytes` | 65 536 | Hard cap on serialized envelope size. |
| `max_ciphertext_bytes` | 16 384 | Hard cap on `SendEncryptedMessage.ciphertext`. |
| `max_plaintext_bytes_before_encryption` | 0 | Reserved; the server never sees plaintext. |
| `max_nickname_chars` | 32 | Hard cap on `Hello.nickname`. |
| `max_room_id_chars` | 64 | Hard cap on `room_id`. |
| `max_rooms_per_connection` | 5 | Hard cap on concurrent rooms per connection. |
| `handshake_timeout_ms` | 5 000 | If `HELLO` does not arrive in this window, connection is closed. |
| `ping_interval_ms` | 30 000 | Server heartbeat period. |
| `pong_timeout_ms` | 10 000 | Time after a sent `PING` before considering the client unresponsive. |
| `idle_timeout_ms` | 90 000 | No inbound activity for this long → connection is closed. |

Operator-configurable server-side limits not exposed on the wire include:

- `max_messages_per_minute` (default 20): per-connection encrypted-message rate.
- `max_commands_per_minute` (default 60): per-connection inbound-frame rate.
- `max_outbound_queue_messages` (default 100) and `max_outbound_pending_bytes`
  (default 1 048 576): server-side back-pressure thresholds. A slow client is closed
  with `GOODBYE` reason `POLICY_ERROR` and message `"client too slow"`.
- `max_violations_in_window` (default 3) and `violation_window_ms` (default 60 000):
  threshold for closing on repeated protocol violations.
- `send_time_limit_ms` (default 2 000): the per-write timeout used by Spring's
  `ConcurrentWebSocketSessionDecorator`.

## 12. Disconnect and goodbye

The server signals an intentional close with a `GoodBye` payload inside a
`GhostEnvelope` of type `GOODBYE`. Fields:

- `reason`: a `DisconnectReason` enum value.
- `message`: a short sanitized string. The canonical mapping used by the reference
  server is (see `GoodbyeReasonMessages`):
  - `CLIENT_REQUEST` → `"client requested"`
  - `SERVER_SHUTDOWN` → `"server shutdown"`
  - `IDLE_TIMEOUT` → `"idle timeout"`
  - `PONG_TIMEOUT` → `"pong timeout"`
  - `PROTOCOL_ERROR` → `"protocol error"`
  - `TOO_MANY_VIOLATIONS` → `"too many violations"`
  - `POLICY_ERROR` → `"policy error"`

The reference server's actual `closeWithGoodbye` writes the caller-provided message
verbatim. The canonical table above documents the intended sanitized strings;
implementations should not echo client input into the `Goodbye.message` field.

A client may also send `DISCONNECT` with a `DisconnectReason` payload to request a
graceful close. The reference server responds with `GOODBYE` of reason
`CLIENT_REQUEST` and closes.

`GOODBYE` is written directly to the underlying (undecorated) WebSocket session so
that it bypasses the concurrent-send decorator's pending-bytes/send-time limits. This
makes `GOODBYE` reach the peer even when slow-client back-pressure has already filled
the outbound buffer. A short delayed close (50 ms) follows to make on-the-wire
delivery deterministic.

## 13. Compatibility

The protocol uses Protobuf 3, which gives certain compatibility properties:

- Fields can be added to existing messages at new, unused field numbers without
  breaking older parsers; old fields read those bytes as unknown fields.
- Enum values can be added without breaking older parsers, but a sender must be
  prepared for a peer to receive an `UNSPECIFIED` value if it predates the new
  variant.
- Removing or renumbering fields is a breaking change.
- The `GhostEnvelope` reserves field numbers 8 through 19 for future use, and the
  payload messages reserve trailing field number ranges to leave room for additive
  growth.

The `version` field on `GhostEnvelope` is checked exactly (`"0.1"` must equal the
configured expected value). A future v0.2 server intending to talk to v0.1 clients
would need to either accept both values explicitly or implement explicit version
negotiation. The current reference implementation does not.

## 14. Tested invalid cases

The integration test suite (`GhostBunkerWebSocketIT`) exercises the following
deliberately invalid client behaviors and asserts the server response. This section
documents what the reference server is known to do for each case.

| Case | Expected server behavior |
|---|---|
| `HELLO` with nickname containing emoji (`bob🙂`) | `ERROR` with code in {`BAD_METADATA`, `PROTOCOL_VIOLATION`}. |
| `HELLO` with non-ASCII nickname (`josé`) | `ERROR` with code in {`BAD_METADATA`, `PROTOCOL_VIOLATION`}. |
| `JOIN_ROOM` sent before any `HELLO` (state `AWAITING_HELLO`) | `ERROR` with code in {`PROTOCOL_VIOLATION`, `BAD_METADATA`}. After three such violations within `violation_window_ms`, `GOODBYE` with reason `TOO_MANY_VIOLATIONS` and close. |
| `HELLO` with `version = "0.2"` | `ERROR` with code `UNSUPPORTED_VERSION`. |
| Joining a 6th room when `max_rooms_per_connection = 5` | `ERROR` with code `TOO_MANY_ROOMS`. |
| Oversized envelope (`> max_envelope_bytes` bytes) | `ERROR` with code `BAD_ENVELOPE`, followed by close. |
| Garbage bytes (non-Protobuf) | `ERROR` with code `BAD_ENVELOPE`, then `GOODBYE` with reason `PROTOCOL_ERROR` and close. |
| `SEND_ENCRYPTED_MESSAGE` before any `JOIN_ROOM` | `ERROR` with code `PROTOCOL_VIOLATION`. |
| `SEND_ENCRYPTED_MESSAGE` with `ciphertext.size > max_ciphertext_bytes` | `ERROR` with code `CIPHERTEXT_TOO_LARGE`. |
| Three protocol violations within `violation_window_ms` | `GOODBYE` with reason `TOO_MANY_VIOLATIONS` and close. |

These behaviors are verified end-to-end against a real Spring Boot WebSocket server
on a random port; see `GhostBunkerWebSocketIT` for the exact test code.
