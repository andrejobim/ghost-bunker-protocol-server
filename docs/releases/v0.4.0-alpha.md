# Ghost Bunker Protocol Server v0.4.0-alpha

## Summary

Prepares the reference server for **future multi-node deployment** by introducing scaling
abstractions (`SessionRegistry`, `RoomRegistry`, `PresenceRegistry`, `MessageRouter`,
`MessageBus`, `RateLimitStore`, `BackpressurePolicy`) with in-memory / local / no-op defaults.

**Server-side only** — web client, protocol, and `.proto` are unchanged. No Redis, Kafka, or
database is added.

## Added

- Scaling interfaces under `io.ghostbunker.server.{session,room,presence,routing,bus,rate,backpressure}`.
- Default implementations: `InMemorySessionRegistry`, `InMemoryRoomRegistry`,
  `InMemoryPresenceRegistry`, `LocalMessageRouter`, `NoopMessageBus`, `InMemoryRateLimitStore`,
  `DefaultBackpressurePolicy`.
- `docs/scaling-plan.md` — multi-node design notes and Privacy-Max constraints.

## Changed

- `GhostBunkerWebSocketHandler`, `GracefulShutdownService`, and `GhostBunkerMetrics` depend on
  interfaces instead of concrete registries.
- Renamed `InMemoryGhostSessionRegistry` → `InMemorySessionRegistry` (implements `SessionRegistry`).
- Replaced `PerConnectionRateLimiter` with `InMemoryRateLimitStore` (`RateLimitStore`).
- Replaced `OutboundQueuePolicy` with `DefaultBackpressurePolicy` (`BackpressurePolicy`).
- `MessageRouter` is now an interface; routing logic lives in `LocalMessageRouter`.

## Privacy-Max status

Unchanged: no persistence of ciphertext, payloads, IP, or user identity. `NoopMessageBus` does not
store published bytes.

## Known limitations

- Still **single-node**; `NoopMessageBus` performs no cross-node fan-out.
- Clustered `MessageBus` / registry backends are documented only in `docs/scaling-plan.md`.
