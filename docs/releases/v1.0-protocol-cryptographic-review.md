# v1.0 — Protocol Cryptographic Review (milestone)

**Type:** Documentation / security milestone — **not** a normal implementation release.

**When:** Only after v0.x stabilizes (`docs/production-readiness-plan.md` Phase 1–6 and
reference client staging validation).

**Projects:**

| Repository | Role |
|------------|------|
| `ghost-bunker-protocol-server` | Wire routing, validation, privacy profile |
| `ghost-bunker-web-client` | Reference E2EE (WebCrypto) |
| `ghost-bunker-protocol` (future) | Optional home for `.proto` + normative spec |

---

## Objective

Document and evaluate future cryptographic work **before** implementation. Establish
gates so no stable **v1.0 security claim** appears without independent review.

This milestone **does not** ship new cipher suites, ratchets, or asymmetric crypto.

## Topics evaluated (see crypto-roadmap)

- **X25519** — ECDH for shared secrets; protocol version impact
- **Ed25519** — Sender / device authentication
- **Double Ratchet** — Forward secrecy; likely separate v1 profile
- **Key rotation** — Manual today; normative protocol TBD
- **Replay protection** — Current gaps documented; server policy TBD
- **Out-of-band verification** — Safety numbers / SAS; needs public keys first
- **Multi-device model** — Conflicts with v0.1 Privacy-Max unless scoped
- **Independent cryptographic audit** — Blocking gate for any v1.0 claim

---

## Rules (binding for v0.x work)

1. **Do not** implement advanced crypto (X25519, Ed25519, Double Ratchet, etc.) in
   v0.1 / v0.2 implementation prompts or releases.
2. **Do not** claim cryptographic security until independent review completes and
   findings are addressed or accepted in writing.
3. **Maintain** the v0.1 symmetric room-key model as **experimental only** (see threat
   model §5).
4. **Do not** break compatibility without a versioned migration plan
   (`protocol-migration-plan.md`).
5. **Do not** change `.proto` without a formal protocol version decision (template in
   migration plan §6).
6. **Do not** change server and client crypto/wire interpretation independently without
   passing the compatibility test matrix.

## Independent audit plan

### Scope (proposed)

- Threat model accuracy and completeness
- Client: room key generation, AES-GCM, nonce, AAD, invite-link handling
- Server: no accidental decryption paths; validation bounds; replay/dedup behavior
- Wire: `ghost_bunker_v1.proto` vs implemented validators
- Privacy-Max: logging and metrics against stated profile

### Out of scope (initial audit)

- Formal verification of Java or TypeScript runtime
- Nation-state traffic-analysis resistance
- Third-party hosting provider compliance
